## Resolved: P1-10

**Closed by replacing the hand-rolled P/Invoke layer with the managed binding.**
`SpatialReaderOptions.ReprojectTo` — new public API on this branch — threw
`EntryPointNotFoundException: OGRNewCoordinateTransformation` on every call, so it
was advertised and unusable.

The changelog's own diagnosis was right that P/Invoke was the problem, but its
prescribed fix (`GDALCreateCoordinateTransformation`) would have been a repair of
code that should be deleted. Three findings that change the fix:

1. **The code comment is false for this version.** `Reprojector.cs` claims the
   binding "exposes the CoordinateTransformation handle constructor but not its
   Transform method (a known gap in the official OSGeo binding)". Reflection against
   `osr_csharp 3.11.3.0` shows `OSGeo.OSR.CoordinateTransformation` with
   `ctor(SpatialReference, SpatialReference)` **and**
   `void TransformPoints(Int32 nCount, Double[] x, Double[] y, Double[] z)`. That
   false premise is the only reason ~90 lines of marshalling exist.
2. **Three of the six P/Invoked symbols were wrong**, not one — so renaming the
   single symbol the changelog names trades one crash for another:

   | symbol requested | status | public C API |
   |---|---|---|
   | `OSRNewSpatialReference`, `OSRSetFromUserInput`, `OSRRelease` | correct | — |
   | `OGRNewCoordinateTransformation` | wrong name | `OGRCreateCoordinateTransformation` |
   | `OGR_CT_Transform` | SWIG-internal, lives in `ogrCSharp`'s native module, **not** `libgdal`; also declared with 6 params against a 5-param function | `OCTTransform`, **returns TRUE on success** |
   | `OGR_CT_Destroy` | SWIG-internal | `OGRDestroyCoordinateTransformation` |

   Note `OCTTransform`'s polarity is the inverse of the `OSR_*` calls: routing it
   through the existing `Check(rc, …)` helper (which throws when `rc != 0`) would
   throw on every *successful* transform.
3. **P1-14 sits directly behind it.** Fixing only the symbols converts a loud
   exception into silently transposed coordinates.

### Follow-on to record with the fix

The managed `TransformPoints` returns `void`, discarding `OCTTransform`'s TRUE/FALSE
flag, so **per-point failures are not observable** on the batch path. OGR marks
untransformable points with a `HUGE_VAL` sentinel rather than raising, so the
sentinel is the only available signal — hence the `IsPlausible` guard (`IsFinite` &&
`|v| < 1e15`) in the replacement. This is a mitigation, not a real per-point status;
`TransformPointWithErrorCode` returns an `Int32` code but is single-point, costing
one SWIG call per vertex. Batch + sentinel is the right trade for county footprint
reads — record which side of the trade was taken.

## Confirmed and expanded: P0-5

`CloseRing()` on linestrings and points (P0-5, unchanged) is confirmed, and the new
`LengthMeters` API widens its blast radius. Precise attribution, since the two
closure mechanisms are easy to conflate:

- **`SphericalPerimeter` closes unconditionally** (its own defect, P1-15/P2-11). For
  a 3-vertex open line at 1° steps it returns the closed triangle, **379,639.757 m**
  against a true **222,390.159 m** — **+70.7%**.
- **P0-5's duplicated vertex adds nothing** to the spherical figures: `SphericalArea`
  and `SphericalPerimeter` are both provably invariant to a repeated first/last
  vertex (pinned by `SphericalArea_IsInvariantToTheClosingVertex`). P0-5's inflation
  is on the planar `Part.Perimeter`/`Part.Area` caches.

Fixing P1-15 will *not* close P0-5, and vice versa.
